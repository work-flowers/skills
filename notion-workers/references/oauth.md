## When to Use OAuth vs. Secrets

| Approach | When to Use |
|----------|------------|
| **Secrets** (`ntn workers env set`) | Service uses static API keys, service account tokens, or webhook secrets. Most third-party APIs with server-to-server auth. |
| **OAuth** (`worker.oauth()`) | Service requires user-level authorisation — the user must grant consent via a browser flow. Common for Google APIs, GitHub (when accessing user repos), Salesforce, etc. |

If the API offers both a service account/API key and OAuth, prefer the simpler
option (usually secrets) unless you specifically need per-user access scoping.

## Setup Flow

The OAuth setup has three phases: code, deploy, and authorise.

### Phase 1: Define OAuth in code

```typescript
const myAuth = worker.oauth("myAuth", {
  name: "my-service-oauth",
  authorizationEndpoint: "https://provider.com/oauth/authorize",
  tokenEndpoint: "https://provider.com/oauth/token",
  scope: "read write",
  clientId: process.env.OAUTH_CLIENT_ID ?? "",
  clientSecret: process.env.OAUTH_CLIENT_SECRET ?? "",
});
```

Store the client ID and secret as Worker secrets:

```bash
ntn workers env set OAUTH_CLIENT_ID=your-client-id
ntn workers env set OAUTH_CLIENT_SECRET=your-client-secret
```

### Phase 2: Deploy and configure the provider

```bash
# Deploy the Worker
ntn workers deploy

# Get the redirect URL — this is generated by Notion
ntn workers oauth show-redirect-url
```

Copy the redirect URL and add it to your OAuth provider's application settings
as an authorised redirect URI.

### Phase 3: Authorise

```bash
# Start the OAuth flow — opens a browser
ntn workers oauth start myAuth
```

Complete the consent flow in the browser. The token is stored securely by the
platform.

### Phase 4: Use the token in tools/syncs

```typescript
worker.tool("getMyData", {
  title: "Get My Data",
  description: "Fetches data from the connected service",
  schema: j.object({}),
  execute: async () => {
    const token = await myAuth.accessToken();
    const response = await fetch("https://api.provider.com/data", {
      headers: { Authorization: `Bearer ${token}` },
    });
    return response.json();
  },
});
```

## Google OAuth Example

Google APIs (Analytics, Sheets, Calendar, Drive, etc.) use the same OAuth2
flow with different scopes.

### 1. Create a Google Cloud OAuth app

1. Go to https://console.cloud.google.com/apis/credentials
2. Create an OAuth 2.0 Client ID (type: Web application)
3. Leave the redirect URI blank for now — you'll add it after deploying
4. Enable the relevant API (e.g., Google Analytics Data API) in the API Library
5. Note the Client ID and Client Secret

### 2. Define in code

```typescript
const googleAuth = worker.oauth("googleAuth", {
  name: "google-oauth",
  authorizationEndpoint: "https://accounts.google.com/o/oauth2/v2/auth",
  tokenEndpoint: "https://oauth2.googleapis.com/token",
  scope: "https://www.googleapis.com/auth/analytics.readonly",
  clientId: process.env.GOOGLE_CLIENT_ID ?? "",
  clientSecret: process.env.GOOGLE_CLIENT_SECRET ?? "",
});
```

Common Google scopes:

| Service | Scope |
|---------|-------|
| Analytics (read) | `https://www.googleapis.com/auth/analytics.readonly` |
| Sheets (read) | `https://www.googleapis.com/auth/spreadsheets.readonly` |
| Sheets (read/write) | `https://www.googleapis.com/auth/spreadsheets` |
| Drive (read) | `https://www.googleapis.com/auth/drive.readonly` |
| Calendar (read) | `https://www.googleapis.com/auth/calendar.readonly` |
| Gmail (read) | `https://www.googleapis.com/auth/gmail.readonly` |

### 3. Store secrets and deploy

```bash
ntn workers env set GOOGLE_CLIENT_ID=your-client-id.apps.googleusercontent.com
ntn workers env set GOOGLE_CLIENT_SECRET=GOCSPx-your-secret
ntn workers deploy
```

### 4. Configure redirect URI

```bash
ntn workers oauth show-redirect-url
# Copy the output URL
```

Go back to Google Cloud Console → Credentials → your OAuth client → add the
redirect URL as an Authorised redirect URI.

### 5. Authorise

```bash
ntn workers oauth start googleAuth
```

### Google-specific notes

- Google tokens expire after 1 hour. The platform should handle refresh
  automatically, but during alpha, token refresh may fail silently. If syncs
  start erroring after working initially, re-run `ntn workers oauth start`.
- If the Google Cloud project is in "Testing" mode, only test users you've
  added can authorise. Switch to "Production" (and complete verification if
  needed) for broader access.
- For service-to-service access (no user consent needed), consider using a
  Google Service Account key stored as a secret instead of OAuth. This avoids
  the token refresh issue entirely.

## GitHub OAuth Example

```typescript
const githubAuth = worker.oauth("githubAuth", {
  name: "github-oauth",
  authorizationEndpoint: "https://github.com/login/oauth/authorize",
  tokenEndpoint: "https://github.com/login/oauth/access_token",
  scope: "repo user",
  clientId: process.env.GITHUB_CLIENT_ID ?? "",
  clientSecret: process.env.GITHUB_CLIENT_SECRET ?? "",
});
```

1. Create a GitHub OAuth App at https://github.com/settings/developers
2. Set the redirect URL from `ntn workers oauth show-redirect-url`
3. Store credentials: `ntn workers env set GITHUB_CLIENT_ID=... GITHUB_CLIENT_SECRET=...`

GitHub tokens don't expire by default (classic OAuth apps), so token refresh
is less of a concern.

## Generic OAuth2 Pattern

For any OAuth2-compliant provider:

```typescript
const serviceAuth = worker.oauth("serviceAuth", {
  name: "service-oauth",
  authorizationEndpoint: "https://provider.com/oauth/authorize",
  tokenEndpoint: "https://provider.com/oauth/token",
  scope: "read write",
  clientId: process.env.SERVICE_CLIENT_ID ?? "",
  clientSecret: process.env.SERVICE_CLIENT_SECRET ?? "",
});
```

The flow is always:
1. Store client credentials as secrets
2. Deploy
3. Get redirect URL → configure in provider
4. Start OAuth flow → authorise in browser
5. Use `await serviceAuth.accessToken()` in tool/sync code

## Token Refresh

The Workers platform handles token refresh automatically using the refresh
token obtained during the initial authorisation. However, during alpha:

- **Refresh may fail silently.** If a sync or tool starts returning auth
  errors after previously working, re-authorise:
  ```bash
  ntn workers oauth start <oauthName>
  ```
- **Some providers revoke refresh tokens** after a period of inactivity or
  after a certain number of refreshes. Google, for example, may revoke
  refresh tokens for apps in "Testing" mode after 7 days.
- **There's no CLI command to check token status** during alpha. Diagnose via
  logs: `ntn workers runs logs <runId>`.

## Troubleshooting

| Symptom | Likely Cause | Fix |
|---------|-------------|-----|
| `invalid_client` error during OAuth | Wrong client ID or secret | Verify secrets: `ntn workers env pull` and check `.env` |
| `redirect_uri_mismatch` error | Redirect URL not configured in provider | Run `ntn workers oauth show-redirect-url` and add to provider settings |
| Token works initially, then stops | Refresh token expired or revoked | Re-run `ntn workers oauth start <name>` |
| `insufficient_scope` error | Missing required API scope | Update the `scope` field in `worker.oauth()`, redeploy, and re-authorise |
| OAuth flow opens but fails to complete | Provider app in testing/sandbox mode | Check provider settings — may need to add test users or switch to production |
| `ntn workers oauth start` hangs | Browser didn't open or callback failed | Try copying the URL manually, or check network/firewall settings |
